## §0. System Overview & Orchestration

The Hierarchical AI Meteorologist operates as a three-block pipeline, ensuring that unstructured natural language forecast reports generated by LLMs are factually verified against raw weather observation data and meteorological physics.

### Pipeline Blocks
```
+------------------------------------------------------------------------+
|                                                                        |
|  [ Block 1: Context Preparation ]                                      |
|  Gathers location data, daily/6-hour/hourly records, climatology, etc.  |
|                                                                        |
+-----------------------------------+------------------------------------+
                                    |
                                    v [ContextPayload]
+------------------------------------------------------------------------+
|                                                                        |
|  [ Block 2: Meteorologist Agent ]                                      |
|  - Generates forecast narrative, claims list, and causal chain.       |
|  - Executes 4 verification engines to compute confidence scores.      |
|  - Triggers iterative loop/feedback if score < threshold (0.55).       |
|                                                                        |
+-----------------------------------+------------------------------------+
                                    |
                                    v [MeteorologistOutput]
+------------------------------------------------------------------------+
|                                                                        |
|  [ Block 3: Report Writer ]                                            |
|  Polishes the narrative into the final structured report.             |
|                                                                        |
+------------------------------------------------------------------------+
```

### Pipeline Orchestration
The main pipeline orchestration and verification validation flow occurs in:
* **File:** [app/llm/meteorologist.py](file:///c:/Users/Krish%20Vinod/Hierarchical_ai_meteorologist_/app/llm/meteorologist.py)
* **Function:** `run_meteorologist(ctx: ContextPayload, *, use_cache: bool = True)` (Lines 27–148)

The verification lifecycle follows these steps within the function:
1. **Preparation (Lines 40–50):** Observational inputs are loaded into Pandas DataFrames (`hourly_df`, `six_hour_df`, `daily_df`, `current_df`).
2. **Instantiation (Lines 52–57):** The validator components are initialized:
   * `DataFactValidator` (Line 53)
   * `MeteorologicalRuleEngine` (Line 54)
   * `CausalGraph` (Line 55)
   * `TemporalConsistencyChecker` (Line 56)
   * `ConfidenceScorer` (Line 57)
3. **Execution Loop (Lines 66–120):** 
   * A call to the Gemini LLM is made to parse the meteorologist's forecast narrative, claims list, and causal chain (Lines 68–77).
   * **Verification Engines execution (Lines 83–86):**
     ```python
     fact_results = fact_validator.validate_all_claims(claims, hourly_df, six_hour_df, daily_df, current_df)
     rule_results = rule_engine.validate_rules(claims, causal_chain)
     ```

   * **Feedback & Retry (Lines 97–120):** If `score < threshold` (default is `0.55`), the system builds detailed critique feedback listing all failed checks, appends it to the prompt, and retries if `max_retry_attempts > 0` (which is set to `0` by default, meaning no retries / only 1 initial attempt occurs unless configured otherwise).
4. **Recording Metrics (Lines 127–138):** Results are logged to `.cache/evaluation_log.json` via the `EvaluationTracker`.

## §1. Meteorological Rule Engine (`MeteorologicalRuleEngine`)

* **File:** [app/verification/rule_engine.py](file:///c:/Users/Krish%20Vinod/Hierarchical_ai_meteorologist_/app/verification/rule_engine.py)
* **Class:** `MeteorologicalRuleEngine` (Lines 9–493)

The Rule Engine checks if the claims and causal chains follow defined physical relationships. It parses rules from `met_rules.yaml` (which contains expected physical bounds, antecedents, consequents, expected lag hours, and confidence weights).

### Key Internal Methods & Logic

#### 1. Constructor & Configuration Mapping (Lines 10–41)
Sets up synonym mapping for events (e.g. mapping `humidity_rise` to `high_humidity`) and binds node names to variables and change directions:
```python
self.event_to_var_dir = {
    "pressure_drop": ("pressure_change_6h", "down"),
    "pressure_rise": ("pressure_change_6h", "up"),
    "stable_pressure": ("pressure_change_6h", "neutral"),
    "wind_increase": ("wind_speed", "up"),
    "light_winds": ("wind_speed", "down"),
    "wind_gusts": ("wind_gust", "up"),
    "high_humidity": ("relative_humidity", "up"),
    "dry_air": ("relative_humidity", "down"),
    "rainfall": ("precipitation", "up"),
    "no_rain": ("precipitation", "down"),
    "extreme_heat": ("temperature", "up"),
    "warming": ("temperature_change", "up"),
    "cooling": ("temperature_change", "down"),
    "low_visibility": ("visibility", "down"),
    "fog_persistence": ("fog_persistence", "neutral"),
    "thunderstorm": ("weather_category", "up"),
}
```

#### 2. Logical Direction Extraction (Lines 55–85 and 87–121)
* `_get_rule_var_direction(var, cond)` determines the expected direction of change (`up`, `down`, or `neutral`) for a rule antecedent/consequent based on the operator.
* `_get_claim_var_direction(claim)` determines the asserted direction of change from a parsed claim by examining its `assertion_type` and `threshold_or_delta`.

#### 3. Error Margin Management (Lines 123–141)
`_get_variable_margin(var)` returns safety buffers to prevent false flags due to data noise (e.g., `temperature` = `1.0°C`, `relative_humidity` = `5.0%`, `pressure` = `2.0 hPa`, `precipitation` = `0.5 mm`).

#### 4. Magnitude Matching and the 50% Guard (Lines 167–230)
`_is_magnitude_matched(rule_ant, claim)` checks if a claim's numeric value satisfies a rule's threshold. It includes a **50% magnitude guard** to prevent rule firing on weak or opposite magnitude matches:
* For **increasing/up** rules (e.g. rising temperature): The claim value must be $\ge 50\%$ of the rule threshold. If not, it is immediately discarded (`return False`).
* For **decreasing/down** rules: The claim value must be $\le 150\%$ of the rule threshold. If not, it is discarded.
* If the guard passes, it applies the standard check incorporating the variable margin (e.g., `claim_val >= rule_val + margin`).

#### 5. Rule Firing Paths in `validate_rules()` (Lines 243–492)
A rule is evaluated via a **dual-path firing system**:

##### Path A: Firing via Claims list
1. **Antecedent Matching:** Finds if claims match all rule antecedents in variable type and direction, and satisfy the magnitude/50% guard (Lines 282–289).
2. **Time Window Overlap:** Verifies that all matching antecedent claims overlap in time (Lines 290–303).
3. **Consequent Checking:** Checks if a corresponding consequent claim is present in the expected lag window (`lag - 3.0` hours to `lag + 6.0` hours) (Lines 306–344).
4. **Contradiction Check:** If a consequent claim is found but asserts the opposite direction, the rule is marked violated. If no consequent is present at all, it's flagged as missing.

##### Path B: Firing via Causal Chain
1. **Antecedent Matching:** Maps antecedents to causal chain event nodes (Lines 350–360).
2. **Duplicate/Indices Tracking:** Resolves all index occurrences of each antecedent node in the causal chain (Lines 362–369).
3. **Categorical Guard:** Relies on chain firing **only** for rules whose antecedents have categorical/string thresholds. Numeric-threshold rules must fire via Path A only (Lines 370–382).
4. **Consequent Order Validation:** Checks if the consequent event appears in the chain *after* all antecedent events. If a contradicting consequent event appears after the antecedents, it is flagged as violated (Lines 384–417).

##### Fallback Logic (Lines 418–452)
If a rule fires via Path A but the consequent is missing from the claims list, the engine checks Path B. If the rule is satisfied in the causal chain (Path B), it is treated as satisfied. However, if a consequent claim exists but explicitly contradicts the rule, the failure is final and does not fall back to the causal chain.

## §2. Causal Graph Engine (`CausalGraph`)

* **File:** [app/verification/causal_graph.py](file:///c:/Users/Krish%20Vinod/Hierarchical_ai_meteorologist_/app/verification/causal_graph.py)
* **Class:** `CausalGraph` (Lines 6–290)

The Causal Graph Engine (Causa Engine) builds a directed acyclic graph (DAG) using `networkx.DiGraph`. It verifies that the LLM's step-by-step causal claims represent physically valid weather patterns.

### Configuration & Graph Building

* **Yaml Parsing (Lines 121–167):** Rules are parsed from `met_rules.yaml`. The engine maps variable thresholds to categorical graph nodes using `_map_var_to_node` (e.g. `pressure_change_6h <= -3.0` maps to the node `pressure_drop`).
* **Graph Edges:** Directional edges are created from the antecedent node to the consequent node, storing attributes `confidence`, `lag`, and `rule_id` (Lines 158–167).

### Critical System Links & Forbidden Transitions

To ensure the graph represents complete meteorological relationships, the engine injects **14 system links** (Lines 171–188) and **5 forbidden/physically impossible edges** (Lines 24–30).

#### 14 Injected System Links:
| Source Node | Target Node | Confidence | Lag (hrs) | Rule ID |
| :--- | :--- | :--- | :--- | :--- |
| `low_visibility` | `fog_persistence` | 0.90 | 0.0 | SYS_LINK_001 |
| `high_humidity` | `low_visibility` | 0.80 | 1.0 | SYS_LINK_002 |
| `stable_pressure` | `light_winds` | 0.80 | 0.0 | SYS_LINK_003 |
| `light_winds` | `no_rain` | 0.75 | 0.0 | SYS_LINK_004 |
| `no_rain` | `warming` | 0.70 | 1.0 | SYS_LINK_005 |
| `warming` | `dry_air` | 0.75 | 1.0 | SYS_LINK_006 |
| `dry_air` | `extreme_heat` | 0.65 | 2.0 | SYS_LINK_007 |
| `extreme_heat` | `cooling` | 0.70 | 6.0 | SYS_LINK_008 |
| `pressure_drop` | `high_humidity` | 0.80 | 2.0 | SYS_LINK_009 |
| `wind_increase` | `thunderstorm` | 0.75 | 1.0 | SYS_LINK_010 |
| `fog_persistence` | `cooling` | 0.70 | 2.0 | SYS_LINK_011 |
| `wind_gusts` | `warming` | 0.65 | 1.0 | SYS_LINK_012 |
| `rainfall` | `thunderstorm` | 0.80 | 0.0 | SYS_LINK_013 |
| `thunderstorm` | `wind_gusts` | 0.85 | 0.0 | SYS_LINK_014 |

#### 5 Forbidden Transitions (`self.invalid_edges`):
1. `dry_air` $\rightarrow$ `rainfall`
2. `dry_air` $\rightarrow$ `fog_formation` *(Note: Since `fog_formation` is normalized to `low_visibility` beforehand, this check is bypassed in practice and cannot trigger)*
3. `dry_air` $\rightarrow$ `fog_persistence`
4. `cooling` $\rightarrow$ `extreme_heat`
5. `clearing` $\rightarrow$ `rainfall`

### Causal Chain Validation (`validate_chain()`)
The validation of a causal chain (e.g. `["pressure_drop", "wind_increase", "rainfall"]`) runs in 4 steps (Lines 190–289):
1. **Forbidden Edge Check:** If any adjacent pair $u \rightarrow v$ in the chain is in the forbidden edges set, `has_forbidden_edges` is marked `True`, and the final `validity_score` is immediately zeroed out (`0.0`).
2. **Direct Edge:** If a direct edge exists in the graph, it records the confidence weight of that edge.
3. **Indirect Path & Path Length Penalty:** If no direct edge exists but a path exists between $u$ and $v$:
   * It extracts the shortest path.
   * Any nodes in this path that are missing from the LLM's chain are flagged in `missing_intermediates`.
   * **Cumulative Path Confidence:** It multiplies the confidence of all edges along the path, then divides by the path length ($N-1$) to penalize long jumps.
4. **No Path (Unlinked):** If no path exists, the transition is logged as invalid, and gets a score of `0.0`.
5. **Entire Chain Connectivity:** A final check extracts the shortest path from the start node of the chain to the end node, appending any omitted nodes to `missing_intermediates` (Lines 266–274).

## §3. Comparison: Rule Engine vs Causal Graph

While both components parse `met_rules.yaml` and model physical relationships, they serve different validation goals and use distinct evaluation strategies:

| Dimension | Meteorological Rule Engine | Causal Graph (Causa Engine) |
| :--- | :--- | :--- |
| **Primary Goal** | Assesses temporal matching and consistency of physical laws across the claims list. | Assesses step-by-step physical causality of the narrative chain. |
| **Core Data Structure**| Python list iteration, Pydantic objects, Pandas DataFrames. | Directed Acyclic Graph (NetworkX `DiGraph`). |
| **Inputs Evaluated** | Claims list (`claims`), causal chain (`causal_chain`). | Causal chain (`causal_chain` only). |
| **Logic Formulation** | $A \implies B$ (with expected lag window). | Connected network flow $A \rightarrow B \rightarrow C$. |
| **Evaluation Path** | Dual-path (Path A: Claims overlap; Path B: Chain index ordering). | Network traversal (Direct edge vs Shortest-path). |
| **Forbidden Elements**| Explicitly contradicts consequent directions in the lag window. | Explicitly invalid transition pairs (Forbidden Edges). |
| **Severity Scoring** | Fired rule penalties subtract from score. | Path length penalties, forbidden edges zero out score. |
| **Time Awareness** | Temporal overlap bounds, lag offset tolerance (`lag - 3h` to `+6h`). | Conceptual time step progression (sequential index checks). |
| **Threshold Matching**| Numeric range comparison, 50% magnitude guard. | Mapped to categorical weather state nodes. |
| **Weights Role** | Component score is the weighted average of fired rules. | Edge confidence weights dictate cumulative path strength. |

## §4. Data Fact Validator (`DataFactValidator`)

* **File:** [app/verification/data_validator.py](file:///c:/Users/Krish Vinod/Hierarchical_ai_meteorologist_/app/verification/data_validator.py)
* **Class:** `DataFactValidator` (Lines 28–515)

The Data Fact Validator compares claims extracted from the narrative text against factual tabular weather observations.

### Claim Schema Validation
Claims are validated against the `WeatherClaim` Pydantic model defined in [app/schemas.py](file:///c:/Users/Krish%20Vinod/Hierarchical_ai_meteorologist_/app/schemas.py#L116-L126):
* `claim_id`: Unique identifier (e.g. `CLAIM_001`).
* `variable`: Weather variable (e.g. `temperature`, `wind_speed`, `precipitation`).
* `assertion_type`: Narrative assertion (e.g. `trend`, `threshold_exceeded`, `category_match`).
* `window_start_utc` & `window_end_utc`: Time boundaries of the assertion.
* `threshold_or_delta`: Expected numeric condition or category (e.g. `> 25.0`, `1.32 to 3.32`, `moderate`).
* `data_scale`: Source scale (`hourly`, `six_hour`, `daily`, `current`, `climatology`).

### Execution Steps in `validate_all_claims()`
For each claim, the validator performs the following sequence:
1. **Scale Routing (Lines 227–238):** Maps the claim's `data_scale` to the appropriate DataFrame (`hourly_df`, `six_hour_df`, `daily_df`, or `current_df`).
2. **Time Window Filtering (Lines 240–277):** Converts timestamps to timezone-aware UTC and filters the routed DataFrame to the `[window_start_utc, window_end_utc]` range.
3. **Column Map Resolving (Lines 279–291):** Maps user-friendly variable names to actual database columns depending on the scale:

| Input Variable Name | Hourly Column Name | Daily / 6-Hour Column Name |
| :--- | :--- | :--- |
| `temperature` / `temp` | `t_c` | `t_mean_c` (mean), `t_min_c` (min), `t_max_c` (max) |
| `apparent_temperature`| `t_feel_c` | `t_feel_c` |
| `dew_point` / `dewpoint`| `td_c` | `td_mean_c` |
| `relative_humidity` / `humidity` | `rh_percent` | `rh_mean_percent` |
| `wind_speed` | `wind_speed_ms` | `wind_speed_mean_ms` |
| `wind_gust` / `wind_gusts` | `wind_gust_ms` | `wind_speed_mean_ms` |
| `precipitation` / `precipitation_mm` | `precipitation_mm` | `precipitation_sum_mm` |
| `visibility` | `visibility_m` | `visibility_mean_m` |
| `pressure` | `pressure_hpa` | `pressure_mean_hpa` |

4. **DataType Checks (Lines 293–330):**
   * Non-numeric columns (e.g. weather condition strings) use text parsing to check if the expected condition is a substring of the observed value.
   * Numeric columns extract values and drop null entries.
5. **Assertion Parsing & Evaluation (Lines 331–512):**
   * **Trend Assertion (Lines 335–377):** Fits a linear regression slope over the sequence of observed data points and computes a monotonic step ratio ($\frac{\text{matching steps}}{\text{total steps}}$). To pass, the slope must match the direction and the monotonic step ratio must be $\ge 0.50$ (50%).
   * **Category Match (Lines 379–460):** Resolves descriptive terms (e.g., `moderate wind`) to numeric ranges using `thresholds.yaml`. If the config defines a range (e.g., `min` and `max`), the claim passes if $\ge 50\%$ of the observations in the window fall within that range. If it represents a temperature drop/rise, it evaluates the change using a robust delta (mean of last third of values minus mean of first third of values).
   * **Threshold Exceeded (Lines 462–512):** Parses operators (`>`, `>=`, `<`, `<=`, `==`, or ranges like `10 to 20`). The claim passes if the condition is satisfied in at least 25% of the observations in the time window.

## §5. Temporal Consistency Checker (`TemporalConsistencyChecker`)

* **File:** [app/verification/temporal_checker.py](file:///c:/Users/Krish%20Vinod/Hierarchical_ai_meteorologist_/app/verification/temporal_checker.py)
* **Class:** `TemporalConsistencyChecker` (Lines 6–142)

The Temporal Consistency Checker prevents contradictions between claims made at different observation scales. It ensures that macro-scale (daily) narratives do not conflict with micro-scale (hourly) details.

### Consistency Checker Logic
1. **Grouping (Lines 61–68):** Claims are categorized by scale into `daily`, `six_hour`, and `hourly`.
2. **Direction Resolution (Lines 31–39):** `_get_claim_direction(claim)` flags whether the claim is asserting an upward trend (`up`), downward trend (`down`), or is flat/neutral (`neutral`).
3. **Pairwise Contradiction Checking (Lines 73–118):** Iterates through overlapping time windows and evaluates direction consistency across scales:
   * **Daily vs. 6-Hour** (Lines 105–107)
   * **6-Hour vs. Hourly** (Lines 110–112)
   * **Daily vs. Hourly** (Lines 115–117)
4. **Conflict Scoring (Lines 121–130):**
   * If two claims for the same variable overlap in time, but assert opposite directions (e.g., Daily temperature is "increasing" while Hourly is "decreasing"), a contradiction is recorded.
   * High-severity contradictions subtract `1.0` from the consistency score.
   * Medium-severity warnings subtract `0.5`.
   * The final consistency score is calculated as:
     $$\text{Consistency Score} = \max\left(0.0, 1.0 - \frac{\text{Penalties}}{\text{Total Checked Scale Pairs}}\right)$$

## §6. Confidence Scorer (`ConfidenceScorer`)

* **File:** [app/verification/confidence_scorer.py](file:///c:/Users/Krish%20Vinod/Hierarchical_ai_meteorologist_/app/verification/confidence_scorer.py)
* **Class:** `ConfidenceScorer` (Lines 5–184)

The Confidence Scorer aggregates verification scores from the 4 validation modules into a single index. It parses weights from `verification_weights.yaml`.

### Weights Configuration
The default weights defined in `verification_weights.yaml` are:
* `data_fact`: `0.35`
* `causal_graph`: `0.20`
* `temporal_consistency`: `0.20`
* `met_rule`: `0.10`

### Hybrid Scoring Formula
To guarantee that a critical failure in any core component immediately drops the overall score to zero, the scorer uses a **weighted harmonic mean** for the physical validation components, and then incorporates the rule engine score **arithmetically** (Lines 73–86).

#### Zero-Guard Condition
If any of the three core physical components has a score of `0.0`, the overall confidence score is zeroed:
$$\text{If } S_{\text{data\_fact}} = 0 \text{ or } S_{\text{causal\_graph}} = 0 \text{ or } S_{\text{temporal\_consistency}} = 0 \implies \text{Overall Score} = 0.0$$

#### Score Aggregation
If all core components are non-zero:
1. **Base Harmonic Score ($H$):**
   $$H = \frac{W_{\text{data\_fact}} + W_{\text{causal\_graph}} + W_{\text{temporal\_consistency}}}{\frac{W_{\text{data\_fact}}}{S_{\text{data\_fact}}} + \frac{W_{\text{causal\_graph}}}{S_{\text{causal\_graph}}} + \frac{W_{\text{temporal\_consistency}}}{S_{\text{temporal\_consistency}}}}$$
2. **Overall Score:**
   $$\text{Overall Score} = \frac{H \times (W_{\text{data\_fact}} + W_{\text{causal\_graph}} + W_{\text{temporal\_consistency}}) + S_{\text{met\_rule}} \times W_{\text{met\_rule}}}{W_{\text{data\_fact}} + W_{\text{causal\_graph}} + W_{\text{temporal\_consistency}} + W_{\text{met\_rule}}}$$

Using default weights:
$$\text{Overall Score} = \frac{H \times 0.75 + S_{\text{met\_rule}} \times 0.10}{0.85}$$

### Issue Ranking & Severity Mapping
Failures are collected across all components, ranked by severity (`high` $\rightarrow$ `medium` $\rightarrow$ `low`), and formatted into a text summary:
* **High Severity:** Meteorological rule violations (`met_rule`), forbidden edges/unlinked transitions (`causal_graph`), and high-severity cross-scale contradictions (`temporal_consistency`).
* **Medium Severity:** Failed data checks (`data_fact`) and medium-severity scale contradictions.
* **Low Severity:** Missing intermediate events (`causal_graph`).

## §7. Evaluation Tracker (`EvaluationTracker`)

* **File:** [app/verification/evaluator.py](file:///c:/Users/Krish%20Vinod/Hierarchical_ai_meteorologist_/app/verification/evaluator.py)
* **Class:** `EvaluationTracker` (Lines 22–243)

The Evaluation Tracker logs metrics for each run to evaluate pipeline accuracy and track system performance over time.

### The Six Evaluation Metrics
The tracker computes the following metrics in `_compute_metrics()` (Lines 34–131):

1. **False Claim Rate:** The fraction of generated factual claims that failed data verification.
   $$\text{False Claim Rate} = \frac{\text{Failed Claims}}{\text{Total Claims}}$$
2. **Cross-Scale Consistency:** `True` if no high-severity scale contradictions were detected.
3. **Verified Report:** `True` if the final score is $\ge$ verification threshold (default `0.55`).
4. **Correction Rate (Correction Needed):** `True` if any `high` or `medium` severity failure is present in the confidence report.
5. **Approximate Hallucination Precision:** Measures the corroboration accuracy of fact-checking failures by checking if data failures correlate with physical rule/graph failures.
   $$\text{Hallucination Precision} = \frac{\text{Corroborated Failures}}{\text{Failed Claims}}$$
   * *Logic:* If any structural failure is found (`rule_violations > 0` or `has_causal_failure = True`), all failed claims are treated as corroborated.
6. **Approximate Hallucination Recall:** The fraction of rule violations matched by a data check failure.
   $$\text{Hallucination Recall} = \frac{\text{Recalled Violations}}{\text{Total Rule Violations}}$$
   * *Logic:* If a rule violation occurs and there is at least one failed claim, the recall is `1.0` (all violations are recalled).
